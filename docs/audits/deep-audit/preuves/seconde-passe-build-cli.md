# Seconde passe build, release, CLI et legacy

Lecture seule après RV01 `c91b9f9`. Pas de source modifiée, de suppression, de Xcode ni de nouveau test artificiel. Les lectures intégrales de première passe restent dans `reprise-build.md` ; cette passe examine les consommateurs et les divergences possibles, sans étendre la certification aux sources UI/PDF.

- **Versions :** `Dependency/version/Makefile:4` → `generate_version_header.sh` → `utils.sh`, puis `MPGlobals.h:9` → `MPArgumentProcessor.m:34,37` pour `--version`. Les deux phases produit app/QuickLook utilisent le même `update_build_number.sh` (RV01). Deux sorties nécessaires — constantes C et métadonnées plist — partagent le même calcul Git. En CI, `release.yml:165,345` fournit le build count et la version explicite à l'action commune ; le helper garde les valeurs Xcode. `build-release.yml:24` omet ces inputs pour son dry run unsigned et laisse donc volontairement les valeurs projet `0`/`0.0.0-dev` ; ses artefacts manuels portent le SHA et ne sont pas publiés par ce workflow. Pas de nouveau défaut version démontré sur le parcours de publication.
- **CSS/Prism :** setup local et action setup installent tous deux le lock npm avec scripts lifecycle désactivés. La cible agrégée MacDownResources du projet est la seule productrice source Prism/CSS ; app et Core en dépendent et copient dans leurs propres produits. Core lit Prism vendor pour son propre bundle, sans régénérer les styles. Aucun second générateur divergent retrouvé.
- **Release :** `release.yml:396,467,559` consomme les helpers sign/verify Sparkle, `staple-release.yml:314` revalide le produit distribué. La répétition des gates correspond aux produits successifs (app puis image publiée), et la signature reste ordonnée composants → QuickLook → parent. Les listes sign/verify sont volontairement identiques pour Sparkle épinglé ; les deux scripts vérifient la présence des composants et le nombre de Mach-O. Pas de retrait des helpers comme supposé code mort.
- **CLI fichiers/dossiers/stdin :** `main.m:30,42,55` écrit trois clés différentes ; `MPPreferences.m:235–269` les lit, puis `MPMainController.m:311,376,419,432` les consomme et les efface. Le partage du domaine stable Release est explicitement fixé dans `MPGlobals.h:21`, tandis que le bundle lancé dépend de DEBUG. Fichiers et dossiers sont deux parcours métier différents, pas deux pipelines concurrents sur les mêmes entrées.
- **Dépréciation ≠ inutilisation :** `main.m` appelle toujours `launchAppWithBundleIdentifier` ; le header NSWorkspace du SDK local le déclare déprécié depuis macOS 11 et propose l'API async. Remplacer ce contrat synchrone exige d'abord valider la propagation d'erreur/fin de processus ; aucune suppression automatique. `MPGetDataMap` emploie encore l'API d'archive dépréciée, mais ses deux appelants lisent exclusivement les ressources du bundle.
- **Legacy candidats conservés :** recherche `rg --hidden` sur code/config (hors git, produits, vendors, preuves) ne trouve aucun import de `Tools/compat.py` ou `Tools/macdown_utils.py`, ni appel de `MPRunningMacDownInstance` en dehors de sa définition. Ces deux scripts peuvent être entrées d'outillage externes ; l'absence d'import interne ne prouve pas leur inutilité hors dépôt. Aucun fichier supprimé.
- **Code caché/maps :** `treat()` (`MPMainController.m:85`) est invoqué à chaque activation et filtre un préfixe de nom utilisateur, des dates MMDD et un tampon journalier. `insertMappedContent` (`NSTextView+Autocomplete.m:470`) consomme l'autre map. Les archives binaires ont été décodées comme plist : `data.map` contient une clé et 2 892 399 octets PNG ; `treats.map` contient le nom `mosky`, trois Markdown/CSS datés (0214/0314/0819) entièrement lus, et un payload .DS_Store jamais sélectionnable par la clé MMDD. Les exemples Python sont des blocs fenced Markdown, pas une exécution Python. Aucun code exécutable caché démontré ; la fonctionnalité est réellement active, donc pas retirée comme legacy. Le dump binaire brut tronqué a été écarté, remplacé par ce décodage structuré ; aucune revendication de lecture ligne par ligne d'octets image.

Empreintes maps décodées : `data.map` SHA-256 `025a921e2605e475deb76107296b8bb76db2b572e74b6b45ee1cf8bea72c3e85`, `treats.map` `dba33b7668fcc5a41df81adc340a73e963590600593fa18fcd923ac7cf372d24`.

Limites : aucune release Developer ID/notarization exécutée sur cette machine, aucune garantie issue d'une recherche négative sur d'éventuels consommateurs externes. Cette passe ne prétend pas prouver absence de tous défauts de concurrence des clés defaults entre processus CLI ; aucun défaut nouveau reproduit pour autoriser une correction certaine.
